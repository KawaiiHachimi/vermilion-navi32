# 2026-11-19: the 1440p input lag, the VRAM layout, and GPU present for frames over 8 MiB (kext b126)

## What boot 7 actually ran (read from Linux: phxboot.log + the unified log)

- `PhxFB: refresh: OTG0 2720x1481 totals, 12 frames in 200609 us -> 60.000 Hz`: the GOP lights the monitor at
  **2560x1440 60 Hz** (CVT reduced blanking totals). The monitor's OSD is not needed for that.
- The daemon turned on phxfb's A/B flip (`flip on (debug.phxfb_flip=1)`), and the flip setup **fits at 1440p**:
  `flip: A at VRAM 0x0 (MC 0x8000000000, FB base 0x8000000000), pitch 2560 px, B at VRAM 0x1000000, 14745600 bytes,
  BAR 0xC80000000+0x10000000`. B may use all of 16-48 MiB (`phxhead::flipBRange(0)`), not 8 MiB as the handoff said.
  The flip only removes tearing: every frame is still copied by the CPU (8-byte loads from the IOSurface, `movnti`
  stores over PCIe) into B. `PhxFB: alias: ... no system-RAM view` is the 780M's carve-out path and is expected on a
  dGPU.
- BAR0 is 256 MiB on macOS (`+0x10000000`); Linux on the same card sees 32 GiB (Resizable BAR). `kFbAperMapMax` is
  512 MiB in the code now (the "160 MiB" in comments and the handoff is old), so the kext maps all 256 MiB.
- Transactions #3 to #600 took 28 s while the owner used the desktop: ~21 frames/s. Not a measurement of the copy time
  (WindowServer presents only what changes), but consistent with a heavy per-frame cost.

## The VRAM layout (code audit + Linux, read-only)

Offsets from the start of VRAM (MC `0x80_0000_0000` on this card, from MMHUB/DCN FB location):

| VRAM | user | source |
|---|---|---|
| 0 - 14.06 MiB | GOP console A at 2560x1440 (up to ~33 MiB at 4K) | phxfb |
| 16 - 48 MiB | phxfb flip B (16 - 30.06 MiB at 1440p) | `phxhead::flipBRange(0)` |
| 24 - 48 MiB | GPU-present slots, 3 x 8 MiB (frames <= 1920x1080x4) | `PHXN_SCAN_SLOT_VRAM` |
| 48 - 49 MiB | PSP ring, cmd, fence | `bringup_navi31.sh` `RING_OFF`, `PHX_VRAM_RING_MIN` |
| 64 - 96 MiB | head 1 surface + its flip B / slots (second monitor) | `phxhead.h` |
| 96 - 116 MiB | PSP TMR (0x1300000 used) | `PHX_VRAM_TMR_*` |
| 128 - 144 MiB | fw_buf (TOC at +15 MiB) | `PHX_VRAM_FWBUF_*` |
| 144 - 146 MiB | SMU driver + tools tables | `PHX_VRAM_SMU_*` |
| 160 - 164 MiB | mesboot GART table, rings, MQDs | `mesboot.c` |
| 164 - 240 MiB | user-VM page tables | `PHX_VRAM_PT_*` |
| 240 MiB - | nothing in Vermilion; every BO is system memory ("E1 backs every BO with system memory") | `phx_globals.cpp` |
| top of VRAM | firmware: DMUB REGION4 near the top on the XT; on the XTX under Linux the PSP TMR at `0x85_fc00_0000`, VRAM reported up to `0x85_feff_ffff` (24560 MiB) | `PhxDmub.h`, Linux log |

Three 14.06 MiB slots do not fit any hole inside the 256 MiB BAR without moving a fixed region (the holes are 15, 12,
14 and 16 MiB). They do not need to: only the GPU writes a slot (the client BO's PTEs point at it, `vmMapVram`) and
only HUBP0 reads it, so a slot needs no CPU view.

Linux, read-only (`amdgpu_regs`, 2026-11-19): DCN_VM_FB_LOCATION_BASE `0x3935` = `0x8000`, **TOP `0x3936` = `0x85ff`**,
FB_OFFSET `0x3937` = 0; MMHUB FB_LOCATION BASE/TOP (`0x1A8EC`/`0x1A8ED`) the same. So `0x3936` is DCN TOP. On macOS the
GOP's value is what counts, so the kext reads it.

## The change: VermilionBoot b126 (built and host-tested; unverified on hardware)

- `PhxScanLayout.h` (pure, `tests/kext/scan_layout_test.cpp` 43/43 on Linux and macOS): a frame up to 8 MiB keeps
  b44's slots at 24/32/40 MiB, exactly as before (the XT's 1080p layout, nothing new checked). A frame over 8 MiB and
  up to 32 MiB (1440p .. 2160p) gets three slots at 256/288/320 MiB, only when the VRAM size (MMHUB) and the display's
  FB window (DCN BASE/TOP) both reach 352 MiB; otherwise the plane is refused as before (CPU copy).
- `phx_scan.cpp`: GEOM_OK, acquire and slot allocation use that layout; the acquire log line names it.
- `debug.phxscan_layout` (read-only, register reads only): the layout the live plane would get, the DCN window, the
  slots in use.
- No new register write, no new message. GPU present still needs `debug.phxscan=1`, which the daemon sets only when
  `/Library/GPUBundles/nvmtl/ws-gpu-present` exists. The plugin (`nvmtl_scanout.c`) and RADV need no change: they size
  the slot buffers from the surface and the kext's checks were the only 8 MiB limit.
