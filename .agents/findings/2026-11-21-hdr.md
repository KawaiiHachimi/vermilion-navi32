# 2026-11-21: HDR on the XTX machine, what Linux sends and what macOS needs

Machine: RX 7900 XTX, LG ULTRAGEAR+ (EDID: PQ, BT.2020, 604 nits). macOS side read from Apple's AMD driver on 2026-11-19
([2026-11-19-refresh-and-hdr.md](2026-11-19-refresh-and-hdr.md), "Step 3"). Linux side from capture v3
(`~/vermilion-captures/capture/display-20261120-130351`, outside git: `to-hdr-<rate>` = Hyprland `cm,hdr` + `bitdepth,10`
from the 144 Hz hub).

## Linux: HDR at every 1440p rate, the same pieces each time

Steady state after `to-hdr-*` (regs.txt), against the plain step at the same rate:

| Register | Plain | HDR | What |
|---|---|---|---|
| HUBP0_DCSURF_SURFACE_CONFIG 0x3AA5, CNVC_CFG0_CNVC_SURFACE_PIXEL_FORMAT 0x418F | 0x8 | **0xa** | scan-out ARGB8888 -> ARGB2101010 (Hyprland's XRGB2101010 buffer) |
| FMT0_FMT_BIT_DEPTH_CONTROL 0x4D01 | 0xc900 | **0xd100** | 8 bpc spatial dither -> 10 bpc |
| FMT0_FMT_DYNAMIC_EXP_CNTL 0x4CFF | 0x11 | 0x1 | |
| DP1_DP_PIXEL_FORMAT 0x56C9 | 0x41000000 | **0x42000000** | 8 -> 10 bpc on the wire |
| DP1_DP_MSA_COLORIMETRY 0x56CA | 0x20000000 | **0x40000000** | MSA MISC0 colour depth |
| MPCC_OGAM0_MPCC_GAMUT_REMAP_MODE 0x90F3 + C11..C34_B | 1 | 2, identity (0x2000 on the diagonal) | |
| OTG0_PIXEL_RATE_CNTL 0x140 | 0xd090 | 0x1d090 | (60 Hz trace; not decoded) |
| DP1_DP_SEC_CNTL 0x56EB | 0x00501111 | **0x00d01111** | bit 23: generic packet 3 on |

All four rates (60 / 120 / 144 / 240) reach 10 bpc, BT.2020, the HDR packet. No MPCC OGAM regamma table is written:
Hyprland encodes PQ itself, as macOS's compositor does in HDR (inferred).

Secondary packets (VPG1, `VPG_GENERIC_PACKET_ACCESS_CTRL` index, then 9 data dwords, then `GSP_IMMEDIATE_UPDATE_CTRL`):

| Slot | Header | Packet | Plain | HDR |
|---|---|---|---|---|
| 0, 1 | `00 07 05 13` | VSC SDP rev 5 (colorimetry / depth) | DB `...0100` | DB `...0206` (10 bpc, BT.2020) |
| 2 | `00 83 1b 04` | AMD FreeSync SPD infoframe (OUI `1a 00 00`) | yes | yes |
| 3 | `00 87 1d 4c` | **HDR mastering (DRM) infoframe**, EOTF 2 = PQ | none | `4c1d8700 00021a01 39088a48 9baa2134 08fc1996 40423d13 0000025b 0114025b 0` |

On macOS today `DP_SEC_CNTL` reads 0x00d01111 (packet 3 on, no packet loaded): the 240 entry plan
(`phx_p0odm_1440p240.inc`, capture v2) carries Linux's value from an HDR state. Harmless (the monitor stays SDR);
the HDR work will load packet 3 anyway.

## macOS: the probe (PhxAccel, `~/gpu/phxboot-hdrprobe`, `debug.phxfb0_hdrprobe`)

Report only, as the Adaptive Sync probe was: head 0's `IOFBTimingRange` (already published for Adaptive Sync) also
reports RGB, 8 / 10 bpc, native / sRGB / BT.709 / BT.2020 and SDR | HDR10, and the connection depths 8 | 10 bpc.
`'hdrm'` (mastering metadata) and `'dsdp'` (Apple's SDP packet) are accepted and logged as raw values (never read
through: they may be user pointers); every `setAttributeForConnection` and `setDisplayMode` depth is logged. No 30-bit
pixel format is offered, no register changes. Question: does System Settings then offer "High Dynamic Range", and what
does CoreDisplay send when it is switched on.

## Probe step 1 on the box (2026-11-21 00:13): no HDR switch

The range was published with HDR10 / BT.2020 / 8-10 bpc; System Settings shows nothing new (owner). CoreDisplay sent
only the usual connection settings (`colr` 0x10001001, `dflg`, `flgs`, `flus`, `bgsc`/`ggsc`/`rgsc`, `vblm`) and
`setDisplayMode(..., depth 0)`; no `'hdrm'`, no `'dsdp'`.

Apple's AMD driver offers four depths per mode (getPixelInformation tables at 0xc17b550..): 16-bit (5 bpc), 32-bit
(8 bpc), **30-bit `--RRRRRRRRRRGGGGGGGGGGBBBBBBBBBB` (10 bpc)** and **64-bit half float `-16FR16FG16FB16`**; PhxAMDFB
offers one (32-bit, maxDepthIndex 0). Its per-mode timing is copied from its own detailed timings (findDisplayMode),
HDR fields included. Probe step 2: a 30-bit depth (index 1; the scan-out stays 8-bit, both copies already narrow l10r)
and the per-mode fields (RGB, 8 bpc, sRGB, SDR).

## Probe step 2 on the box (2026-11-21 23:19) and CoreDisplay's HDR gate

Step 2: macOS took the 30-bit depth (`setDisplayMode(3, depth 1)`), the desktop stayed normal (both copies narrow l10r);
no HDR switch. CoreDisplay (from the shared cache with `dyld_info -disassemble`; `dyld_info -exports` lists
`CoreDisplay_Display_SupportsHDRMode(_Server)`): `CoreDisplay::Display::SupportsHDRMode` is true only when two capability
bits are set (one in the connection's state from `gConnectRefDict`, one in a flags byte; not decoded) **and**
`FindIOModeIDForIODynamicRange(fb, currentModeID, 2 /* kIODynamicRangeHDR10 */)` returns another mode id than the
current one; Apple's own displays (vendor 0x610, some product ids) are handled apart. So HDR needs an HDR10 twin of the
current mode, as Adaptive Sync needed a variable twin. Probe step 3: HDR twins of the four 1440p rates (ids 14-17,
`kStdHdrTwin`, timing info HDR10 / 10 bpc / BT.2020); the fixed modes report SDR.

## Probe step 3 on the box (2026-11-21 23:27): the HDR switch is offered

With the HDR10 twins System Settings shows "High Dynamic Range". Switched on: `setDisplayMode(17, depth 0)` (the twin
of 240, the 32-bit depth); off: `setDisplayMode(6, depth 0)`. No `'hdrm'` or `'dsdp'` attribute. The monitor stays SDR
(nothing sent yet). Apple's AMD driver takes the HDR infoframe through **AGDC 0x713** (`setSecondaryDataPacket`,
`AGDCFBSDPPacket_t`; compare chain in `vendor_doDeviceAttribute`); PhxAGDC's 40-line log cap was used up by 0x711 at
login, so a refused 0x713 would not have shown. Probe step 4: 0x713 accepted and kept (`debug.phxagdc_sdp`).

## Capture v3 has no way back from HDR (2026-11-21 23:40)

Generating HDR replay plans from v3 showed it: every `from-hdr-*` step ends at 144 **in HDR** (DP_PIXEL_FORMAT
0x42000000, FMT 0xd100, DP_SEC_CNTL 0x00d01111, its link at HBR3), and `to-hdr-143.99` / `to-hdr-59.95` start from that
HDR hub (the auto cut-off fails: no full mode set). The tool's SDR rule named no colour mode, so Hyprland kept the
previous step's `cm,hdr`. So v3 holds SDR -> HDR at 60 once and HDR -> HDR switches, but no HDR -> SDR. The plans were
discarded. Fix: v4 of `linux_display_capture.py` names `bitdepth,8,cm,srgb` on SDR steps and `--hdr-pairs` captures SDR
hub -> HDR <r> -> SDR hub for each rate (copied to `/boot/vermilion/capture-tool/`, run in Omarchy).

Also known from probe step 4 (23:31): with HDR switched on, CoreDisplay sends no AGDC 0x713 packet (0 kept) and no
`'hdrm'`: the driver builds the HDR infoframe itself, as Linux does (the replayed plans carry Linux's).

## Capture v4 and the HDR replay modes (VermilionBoot b145, 2026-11-22)

Capture v4 (`display-20261121-234031`, Omarchy session): SDR 144 hub -> HDR at 59.95 / 120 / 143.99 / 239.97 and back;
DP_PIXEL_FORMAT 0x42000000 after each to-hdr, 0x41000000 after each from-hdr. Each switch is **two full mode sets**
(three write bursts; amdgpu commits the mode, then the colour space / depth), each with its own link window (DISABLE,
then ENABLE and training). The generator now takes `--modesets 2` and turns every link window into LINKOFF / LINKUP
with that window's own rate (the committed 28 plans regenerate byte for byte). Links: HDR 60 HBR x4, 120 HBR2, 144 and
240 HBR3 (240 with DSC). The HDR packet (slot 3): entering `4c1d8700 00021a01 ...` (EOTF 2 = PQ, Linux's metadata),
leaving `4c1d8700 00001a01 0...` (EOTF 0, no metadata). b145 adds the four HDR modes to the replay set (keys 1440060 /
1440120 / 1440144 / 1440240); PhxAccel's HDR twins ask for them. The surface stays macOS's 8-bit one (the plans drop pipe
0's surface registers; macOS picked depth 0 for the HDR twin): 10 bpc on the wire from an 8-bit source.

## HDR works on the box (b145, 2026-11-22 00:38)

System Settings' High Dynamic Range on: `head 0 switch to id 17 (target 1440240): DONE: ODM 2:1 + DSC + FEC`; the LG
shows HDR (owner). Off at 00:49: back to id 6 (240 SDR), DONE. Replay engine: 3 runs, 3 done, 0 fall-backs. Afterwards
DP_PIXEL_FORMAT 0x41000000, FMT_BIT_DEPTH_CONTROL 0xc900, DP_SEC_CNTL 0x00501111 (packet 3 off: the 240 entry plan's
leftover enable is gone too).

## 10-bit drawing (b149, 2026-11-22, unverified)

WindowServer's display surface is already 10-bit (`l10r`, x2 R10 G10 B10, the layout of Linux's XRGB2101010 / HUBP format
0xa); both copies narrowed it to 8 bits for the ARGB8888 scan-out. Linux's to-hdr mode sets write CNVC_CFG0
SURFACE_PIXEL_FORMAT 0x418F = 0xa, then HUBP0 DCSURF_SURFACE_CONFIG 0x3AA5 = 0x8, 0xa (each of the two mode sets; pipe 1's
0x42FA / 0x3B81 the same under ODM); from-hdr writes 0x8. The plans dropped pipe 0's surface registers; b149's HDR plans
keep these two (generator `--pixel-format`), and the copies follow the live format (kext scan status FMT10, "phxScanFmt").
MPCC0_MPCC_CONTROL on the box: 0xffff0461 (macOS; Linux 0x422): global alpha in both, so the top two bits of l10r are not
blended.
