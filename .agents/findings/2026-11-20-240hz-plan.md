# 240 Hz HDR on the XTX machine: what macOS needs (2026-11-20, from capture v2)

Inputs: [refresh-and-hdr findings](2026-11-19-refresh-and-hdr.md) ("240 Hz research", "Linux capture v2").

## The link: the existing trainer already speaks Linux's commands

Linux's 22 TRANSMITTER_CONTROL commands for 144 -> 240 equal what `PhxDpLink.h txCmd` builds for a connector with
phy 1 / hpdsel 3 (DP B), dword for dword: header `0x3c000180`; DISABLE `00000001 0 f4130003`; ENABLE `04000101 81000
f4000003`; SETUP_VSEMPH `04xx0b01 81000 f6130003` (xx = dplaneset). Only the symclk dword differs from HBR2 (54000).
The AUX side (DPCD 0x100/0x101/0x102/0x103-0x106, 0x120 FEC, 0x160 DSC) goes through the register AUX engine on
Linux 7.2 (no DMUB AUX), as in `PhxDpLink.h`. TPS4 for EQ is already there.

Changes the trainer needs (each a gate, not new behaviour):
- rate HBR3 (`0x1e`, symclk 81000) allowed;
- DP B as a connector (`{"DP-B", 1, 1, 2?, 2, 3}`: DIG1 / PHY B / HPD / AUX2 / hpdsel 3; the HPD index from the board
  table, unverified) only for the pipe-0 engine's retrain, never for the multiport probe;
- the sink caps from the extended block 0x2200 when 0x00E bit 7 is set (the LG says HBR2 at 0x001, HBR3 at 0x2201);
- the DMCUB gate takes `0x07008748` next to `0x07008742` (PCI rev 0xC8 only).

## The pipe: Linux's exact 240 Hz configuration, not a single pipe

A single pipe without DSC would need a DPPCLK hard minimum near 1.06 GHz, a DAL value Linux never sent on this card, and
HUBP values no capture has. Linux lights 240 Hz (8 and 10 bpc, SDR and HDR) only one way here: **HBR3 x4 + FEC + DSC
(16 bpp, 2 slices per half) + ODM 2:1** (OTG0 -> OPP0 + OPP1, HUBP0 + HUBP1 each scanning half of the same surface,
DSC0 + DSC1), 2 pixels per cycle, DISPCLK 537.5 MHz, DET 9/9/0/0. Every register value for it is in the 240 / 240-10 /
hdr-240 traces. So the 240 Hz plan follows that; 10 bpc / HDR at 240 is then the same plan with the 10 bpc DSC/PPS values.

Consequences on macOS:
- the flip path must write both HUBP0 and HUBP1 surface addresses (HUBP1 at viewport x 1280) at 240 Hz;
- pipe 1 (HUBP1 / DPP1 / MPCC1 / OPP1 / DSC1) must be free: refuse when OTG1 runs (the second-monitor case);
- the 2-pixel-per-cycle DTO convention (phase = pclk / 2) only for this plan.

## Order (one kext change per boot)

1. **D1 retrain at the same rate:** the pipe-0 engine retrains DP B HBR2 -> HBR2 at 1440p60 (stream off, TX DISABLE,
   ENABLE, CR + EQ, stream on). Proves TRANSMITTER_CONTROL on DMCUB `0x07008748` and the DP B gates with no new mode.
   Fall back: retrain again; last resort the next boot (the GOP relights 60 Hz).
2. **D2 HBR3 at 144:** same, at HBR3 with the 144 plan's timing (bandwidth headroom, no DSC): proves HBR3 on this PHY.
3. **E1 240 Hz SDR:** HBR3 + FEC + DSC + ODM 2:1 plan from the 240 trace; head-0 row 240; flip on both HUBPs.
4. **E2 HDR** (separately, also at 60-144): 10-bit surface + 10 bpc output + HDR infoframe + PQ; at 240 the 10 bpc PPS.

## Linux's 144 -> 240 Hz mode set, decoded (capture v2 `display-20261120-065140/240`, read on macOS 2026-11-20)

writes turned back into DPCD accesses (the AUX traffic *is* in the register trace: AUX2 is the register engine). Per-frame
noise left out (OTG interrupt / static-screen / sync-status writes, flips, cursor, audio, FAMS / CAB DMUB). Scripts and the
decoded sequence: outside git (`~/vermilion-captures/`). Times relative to the first write.

So the one-pipe 240 Hz state is only a blank interim on Linux (about 3 ms); the picture always runs on two pipes.
DPPCLK is never raised for one pipe (a 1056 MHz pixel rate through one DPP at ~614 MHz would underflow).

## E1 build plan (240 Hz SDR), next

One engine run = Linux's sequence above, cut into the pipe-0 engine's style (plan tables generated from the capture,
gates, read-backs, fingerprint of everything outside pipes 0 / 1, verify window, fall-back):
1. **Generator** (`tools/capture/p0plan240_from_trace.py`): the filtered write sequence -> `phx_p0_plan_1440p240.inc`
   (ordered steps: W reg/val/mask, DMUB, DPCD, DAL hard min, wait; every step tagged with its phase and source line).
   Dropped on purpose: DAL 0x14 / 0x0e / 0x10 / 0x15 / others (only SetHardMinByFreq 9 for DISPCLK / DPPCLK, as the 120 /
   144 plans), audio, the DPCD source OUI writes (vendor ID, no effect on the stream; unverified), FAMS / CAB DMUB, VRR.
2. **Engine** (PhxPipe0.h or a new PhxPipe0x2.h): 60/120/144 -> 240 and back; the back path is the same structure with the
   1440p144 values (two pipes -> one, DSC / FEC off, HBR2). Uses PhxDpbRetrain's trainer for the link part (+ FEC_READY,
   DPCD 0x120 / 0x160 on the retrain list). Fall-back on any failure: the 144 path.
3. **Flip on both HUBPs** (`phx_scan.cpp` flip: HUBP1 gets the same address when ODM 2:1 is on; under the OTG0 update lock
   so both halves latch on the same frame).
4. **Head-0 mode row 240** (PhxAccel `kHead0Modes`: 2560x1440, 239.96 Hz, 1056.75 MHz, 2720x1619) + target_hz 240.
5. Host test against a register model (both pipes, DSC status, FEC), then one boot with a root-shell test as D1.
Open: HUBP1 / DPP1 power-up on this card (DOMAIN power gating: the trace's DC_IP_REQUEST_CNTL / DOMAINn_PG_CONFIG
sequence), the DPP1 DTO (DPPCLK1_DTO_PARAM), watermarks at 240 (Linux's set A is the firmware's x2, as at 120 / 144).

## E1 first try on hardware (2026-11-20 07:57, b131): stopped at a wait that Linux never ran

Survey passed (FEC 0xbf, DSC 0x01, pipe 1 unclocked and powered: HUBP1_CLK 0x500000, DOMAIN1 status 0x10000000). The 240
run executed 414 writes, 19 waits (max 4.5 ms: power gating, OTG lock / busy, clocks), 2 DAL hard minimums (acknowledged),
the link off (D3, DISABLE, FEC_READY off), then stopped at step 217 (trace line 476): a generated wait for DIG1 FIFO
RESET_DONE after a setup pulse with the link off; RESET_DONE never rose (DIG1_DIG_FIFO_CTRL0 0x11e). The back plan stopped
at the same kind of step: dark until a power cycle. Guard quiet, no stray write. Cause: the generator's FIFO rule; Linux
waits only in enc32_reset_fifo (link up). b132: waits only where Linux's next write carries the RESET_DONE it read.

## b134 from System Settings (2026-11-20 08:38-08:41): 240 works once, the switching does not

Log (PhxFB): 60 -> 144 done, 144 -> 240 **done** (OSD 240), 240 -> 60 refused (b134 design: the 1 ppc plans cannot run after
240), 240 -> 144 done (back plan), 144 -> 120 / 60 refused, 144 -> 240 FAILED at step 0: the first DAL SetHardMinByFreq
(DISPCLK 1075 MHz) was not acknowledged from the back plan's state (it was from the GOP's 144); the engine then ran the back
plan (black flash) and latched `failed`: every later 240 refused. Owner: "the switching is shit".
Cause: two engines (the 1 ppc pipe-0 plans for 60 / 120 / 144, the Linux replay for 240) that do not hand over. Decision:
one replay engine for every mode (Linux's own mode set, always via the 144 hub), from capture v3 (`--all-modes`: every
available mode, VRR at every rate, HDR at every rate, each from the hub and back). Also: a failure before the first write must
not latch; the DAL response must be kept in the stat.
Autologin: the daemon wrote autoLoginUser before the WindowServer restart (log), but loginwindow did not log in: macOS only
auto-logs-in at the first loginwindow of a boot; the restart counts as a logout. Owner: does not matter. Left installed,
inert in effect; removal: `rm ~/gpu/phxboot-autologin; sudo sysadminctl -autologin off`.

## Capture v3 and b135 (2026-11-20 13:00-13:40): one replay engine for every 1440p rate

Capture v3 (Linux 7.2.15, `display-20261120-130351`, outside git; Adaptive Sync on in the monitor for the whole run): all
40 steps `hyprctl: ok`. 12 EDID modes (1440p 59.95 / 120 / 143.99 / 239.97, 1080p 120 / 119.88 / 60, 1280x1024@75,
1024x768@60, 800x600@60.32, 640x480@60 / 59.94), each from Linux's 144 and back; VRR and HDR (10 bpc, `cm,hdr`) at the four
1440p rates. Read on macOS:
- Every switch is one burst of writes, then only per-frame flip / lock writes (a 20 ms gap splits them); the generator now
  finds the end itself (the first OTG0 unlock after the second burst).
- Linux retrains the link at every switch, at the lowest rate that fits: 1440p60 HBR x4, 1440p120 / 144 HBR2 x4, 1440p240
  HBR3 x4, 1080p60 RBR x4, 1024x768 RBR x2, 800x600 / 640x480 RBR x1. FEC is turned on after training at every rate
  (DP_DPHY_CNTL 0x30). The ENABLE symbol clock gives the rate.
- Two pixels per clock at every mode (DP_DTO0_PHASE = pclk / 2, OTG_PIXEL_RATE_DIV unchanged): the 144 hub is the same
  pipe setup for all of them; only 240 adds ODM 2:1 + DSC.
- Linux's totals: V_TOTAL 0x5c8 (60), 0x5f4 (120), 0x5eb (144), 0x652 (240); H_TOTAL 0xa9f at all 1440p rates.
- After a `from-vrr-*` step OTG0 counts 67-72 frames/s at 144 (VRR still active with nothing to draw); after `from-hdr-*`
  the pixel format stays 10 bpc (0x42000000) and M/N changes: hyprctl keeps the depth. Neither matters for SDR replays.
- v3's from-240 differs from v2's back plan in two places: no VPG generic packet (v2 had a zero HDR-metadata SDP) and
  DIG_FIFO_CTRL0 top bits 0x2000 instead of 0x1000.

b135 (VermilionBoot only): PhxP0Odm.h runs a mode set {60, 120, 144 = hub, 240}: six plans from v3 (to / from per rate),
plus b133's entry from macOS's 144. States mac / linux; after the first 240 every rate goes cur -> 144 -> target. A failed
to plan falls back through the target's from plan (lands on 144, not latched; twice = that rate refused for the boot). A
failure before any effect (write, DPCD write, link op, acknowledged DAL) is a plain refusal: b134's step-0 DAL refusal would
now leave the engine usable. Likely cause of b134's DAL refusal (unverified, the response was not kept): `dalMessage`
returns busy without sending when the previous RESP still reads 0, and p2Dal reported that as response 0; p2Dal now waits and
retries for ~2 s like Linux. Host test: every ordered pair of rates twice round, fall-backs, refusals, latches; dropping
to-60's V_TOTAL write or training from-120 at HBR are both caught. Not on hardware yet.
