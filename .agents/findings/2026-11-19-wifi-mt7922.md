# 2026-11-19: Wi-Fi on the XTX machine (MediaTek MT7922), AirportMtkWlan 2.1.6

## The card (Linux, read-only, 2026-11-19)

| | |
|---|---|
| Wi-Fi | `0b:00.0`, MediaTek MT7922 `14c3:0616` rev `0x00`, subsystem `105b:e0cd` (Foxconn), BAR 1 MiB + 32 KiB, MSI; Linux driver `mt7921e` |
| ACPI path | `\_SB_.PCI0.GPP7.UP00.DP58.EP00` (made unconditional by the DSDT NOP patches, `efi/machines/b650e-i-xtx.json`) |
| PCI path | root port `00:02.1` (`1022:14db`) > chipset switch `05:00.0` (`1022:43f4`) > downstream port `06:0b.0` (`1022:43f5`) > the card |
| Bluetooth | **USB `0489:e0e2`** ("MediaTek Inc. Wireless_Device", Foxconn vendor ID), bus 1 port 11, USB 2.0, three interfaces of class `e0`, Linux `btusb`. Earlier docs said `0e8d:0616`: that is wrong for this board |

## The kext: Arxusion/AirportMtkWlan v2.1.6, Tahoe build (research)

- `com.flxxxxddd.AirportMtkWlan` 2.1.6, x86_64, 2.7 MB with the firmware built in. It matches
  `0x061614c3` (IOPCIMatch) and links only Apple's families (IO80211Family, IOSkywalkFamily, corecapture,
  IONetworkingFamily, IOPCIFamily). **No Lilu dependency, no HeliPort-style app**: it is a native AirPort interface
  (the Wi-Fi menu, System Settings, Keychain auto-join).
- Needs `DisableIoMapper = true` (already on for Vermilion) and the native vendor ID (no SSDT hiding the card; we have
  none). README: `MinKernel 25.0.0`, `MaxKernel 25.99.99` for the Tahoe build, because the Sequoia build breaks
  `IO80211SkywalkInterface` vtables on Tahoe. `efi/build.py` now writes a kext's `max_kernel` from `components.json`.
- 2.1.6 is the maintainer's current pick: 2.2.0/2.2.1 (AWDL) panicked for users and were pulled (issue #15, comment
  2026-11-16). The README already describes 2.2.1; ignore that.
- 2.1.6 skips ASPM changes on AMD parent bridges (`parent_vendor == 0x1022`): an older version hard-froze an AMD
  machine as soon as DMA began (issue #11). All of this card's bridges are AMD.
- AWDL (AirDrop) and RSDB are off unless `-mtkawdl` / `-mtkrsdb` are set (2.1.6 release notes). Emergency boot-arg:
  `-mtkwlanoff`. Other boot-args: `mtk_cc=XX`, `-no160`, `-novht`, `-noht40`, `-nohe`, `-mtknoamsdu`,
  `-mtkallowaspm`, `-mtknoparentaspm`, `-mtkforceparentaspm`.
- Similar machines in the issues: #3 (ASUS B650E-F, MT7921K at the same kind of path behind GPP7, Tahoe 26.7.2:
  connection drops after minutes on v2.0.0, fixes in 2.1.0) and #5 (RZ616 `14c3:0616` behind GPP7, 26.7.2: scans and
  WPA2 failed on an old build, fixed in 2.1.0). Nobody has reported 2.1.6 on an RZ616 yet *(as of 2026-11-19)*.
- The kext can't touch the GPU, so hard rule 1 (SMU/PSP/DAL) doesn't apply. Card firmware: Linux's `mt7921e` loads it
  too, so the card is in a Linux state on a warm restart; the owner's cold power-off resets it anyway.

## Boot 2 (2026-11-19): MtkWirelessWifi loaded, never attached either. Read on the Mac itself

First boot worked from macOS directly (T3 Code + Claude Code on the Mac, iPhone USB hotspot for the network).

- **Same failure as boot 1:** `com.dinovn.MtkWirelessWifi (1.1.1)` loaded; its `IOResources` object exists
  (`MtkWirelessWifi = 1`) but `MtkPCIEDeviceWrapper = 0`. Nothing attached under the card (`EP00` under `DP58`);
  no driver lines in `dmesg`.
- **Cause found (mechanism):** the card's IOPCIDevice has `"Capability Offsets" = {}` and none of the keys a
  capability walk sets (`IOPCIExpressCapabilities`, `IOPCIPowerManagementCapabilities`, `IOPCIMSIMessageControl`,
  `IOInterruptSpecifiers`, ...). Both drivers' `probe()` does `findPCICapability(MSI/MSI-X)` and returns NULL
  silently when neither is found (`"No MSI cap"`), so no MediaTek kext can attach while this is so.
- **Where it comes from** (IOPCIFamily-726.100.6 source): `IOPCIBridge::probeBusGated` calls
  `constructCapabilitiesDict(nub)`, which reads the capability pointer (config `0x34`) once; a read of `0xFF`
  (device not answering, or `configAccess()` refused) gives `offset & 3 != 0` -> empty list. The configurator's
  early scan at 0.47 s *did* read the card's PCIe capability (`IOPCIExpressLinkCapabilities = 0x141dc12`, Gen 2 x1,
  set from `device->linkCaps`), so the card answered then and stopped answering by the time the nub was published
  (21 s). The link is up now (`DP58` LinkStatus `0xf012`: Gen 2 x1, DLL active).
- **The I225-V has the same symptom** (`EP00` under `DP50`: empty capability list, published at 10.9 s and again
  at 25.8 s). Its neighbours on the same chipset switch, USB `XH00` (`DP60`) and SATA `SA00` (`DP68`), were
  published at 0.55 s with full capability lists. So the Ethernet fallback (AppleIntelI210Ethernet) would most
  likely fail the same way until this is fixed.
- **Ruled out:** hotplug (`supportsHotPlug 0` for every bridge, so AMD_Vanilla's `IOPCIIsHotplugPort` patch changes
  nothing); config protection or secondary bus reset (no `protectDevice`/reset log lines); L1 substates being turned
  on by macOS (without a device-tree property IOPCIFamily writes 0 to L1PM Control). Also seen: `DP58` has two ACPI
  children at `_ADR 0` (`EP00` and `WIFI`); `DP50` has only `EP00` and fails the same way, so that is not the cause.
  Both broken endpoints carry `acpi-wake-type = 2` (AppleACPIPlatform), the working ones don't; IOPCIFamily doesn't
  read it.

## Boot 3 and live reads (2026-11-19, 08:56-09:15, on the Mac)

- **The first boot of the `vermilion-pcilog` EFI reset by itself** before macOS logged anything (no unified log
  lines, no panic report, no daemon run); the second boot worked. Cause unknown (unverified whether the logging
  boot-args played a part).
- **IOPCIFamily's log (pci_log 0x677):** the configurator found the card at 0.478 s and read its BARs
  (`PFM 0xf810100000`, `MEM 0xdf600000`) and its device capabilities; the nub's `probeBusGated` (30-54 s) logs no
  "link depth" line, i.e. found no PCIe capability. No power, link, reset, protect or "waited for device" lines for
  the card or its ports. Every logged boot (all with Vermilion; the older ones have rotated out) publishes the
  chipset devices at a fixed rhythm: one at ~0.55 s, the next ~10.35 s later, the next ~10.35 s after that.
- **Live config reads** with `tools/capture/pcicfg.c` (IOPCIFamily's diagnostics user client: root + non-zero
  `debug=`): the bridges answer. Wi-Fi port `DP58` (06:0b.0): ASPM L1 enabled (Link Control `0x0002`), link Gen 2
  x1 with data link active, **L1 PM Substates disabled** (L1PM Control 1 `0x60018000`), AER status clean, bus
  routing correct along root port 0:2.1 (5-13) -> upstream port 5:0.0 (6-13) -> 6:0b.0 (11). Ethernet port `DP50`
  identical. USB port `DP60` also has ASPM L1 enabled and works. **Reading the endpoints (0b:00.0, 0a:00.0, 0c:00.0
  in one go) froze the machine** (hard reset): the Wi-Fi and/or Ethernet endpoint really does not answer config
  requests. Never read them again; read their bridges only.
- **Ruled out since boot 2:** L1.2 (disabled on the ports), macOS changing ASPM by default (IOPCIFamily only sets
  ASPM when a boot-arg or property asks, and only from the endpoint's side, which is already silent by then; so
  `pci-dev-aspm-default` would act too late), BAR relocation as the common cause (the I225-V's BARs were not
  moved, yet it fails the same way), ACPI power control (DP50/DP58 `EP00` have only `_PRW` and `_RMV = 0`; the
  extra `DP58.WIFI` node only reads the vendor ID through a PCI_Config region and has no power methods).
- **Still open:** what makes both chipset endpoints stop answering between 0.5 s and ~20 s. The decisive comparison
  is the same path under Linux (`lspci -vvv` as root of 06:0a.0, 06:0b.0, 0a:00.0, 0b:00.0 and `dmesg` PCI lines),
  or one boot with `-phxbringupoff` to rule the GPU bring-up (which runs in that window) in or out.

## Linux side (2026-11-19 18:21, Omarchy, kernel 7.2.15, booted from Limine)

`tools/capture/linux_pci_capture.sh` -> `/boot/vermilion/capture/linux-pci-20261119-182102.txt` (2942 lines, not in
git; MACs and the I225-V's Device Serial Number masked, checked). Both endpoints work here: `0b:00.0` bound to
`mt7921e`, `0a:00.0` to `igc`.

- **The links as the firmware leaves them, unchanged by Linux:** ASPM policy `default`; no `ASPM:`, "common clock
  configuration is inconsistent", retrain, AER or quirk line in the kernel log for this path. Every link on it has
  **Common Clock Configuration set** on both ends, ASPM L1 only (no L0s), all L1 substates disabled; every device in
  D0, runtime-PM `active`, no link power-off.
- **Raw words (PCIe capability at 0x80 on the chipset ports and the card, 0x58 on the root port):**

  | Device | Link Control | Link Status | L1 PM Control 1 |
  |---|---|---|---|
  | 00:02.1 root port GPP7 | `0x0c42` | `0x3044` (16 GT/s x4) | `0x00000000` |
  | 05:00.0 switch upstream | `0x0042` | `0x1044` | `0x60010000` |
  | 06:0b.0 Wi-Fi port DP58 | `0x0c42` | `0x3012` (5 GT/s x1, DLL active) | `0x41168000` |
  | 06:0a.0 Ethernet port DP50 | `0x0c42` | `0x3012` | `0x60018000` |
  | 06:0c.0 USB port DP60 | `0x0042` | `0x1011` | |
  | 0b:00.0 MT7922 | `0x0042` | `0x1012` | `0x41160000` |

  `0x0c00` (bandwidth-management and autonomous-bandwidth interrupt enables) is Linux's PCIe bandwidth-control
  driver; Link Status bits 14/15 are cleared by that driver, so their absence here says nothing.
- **Difference to macOS (boot 3 live reads):** the Wi-Fi port DP58 read **Link Control `0x0002`** in macOS: ASPM L1
  as here, but **Common Clock Configuration clear**, and Link Status `0xf012` has bits 14/15 set (link bandwidth
  management / autonomous bandwidth status: the link was retrained or changed speed/width since they were last
  cleared). Under Linux the same port has Common Clock set and so does the card. So between firmware and the
  endpoints going silent, something in the macOS boot path rewrote DP58's Link Control (clearing Common Clock) and
  the link retrained; a link whose two ends disagree on the common clock fits "link up, endpoint no longer answers"
  *(unverified: the cause, and whether DP50 reads the same in macOS)*. L1 PM Control 1 differs only in timing fields
  Linux reprograms (`T_PowerOn`, `Common_Mode_Restore_Time`); no L1.x enable is set on either OS.
- **Next, on the Mac:** read DP50's Link Control too (bridges only, never the endpoints); look in IOPCIFamily-726
  for writes to Link Control (bit 6 Common Clock, bit 5 Retrain Link) and in the patched DSDT for anything under
  `GPP7.UP00.DP50`/`DP58` that writes PCI config; the `-phxbringupoff` boot still separates the GPU bring-up.
