# 2026-11-23: GPU performance and power (thread 02, measured on the XTX machine)

Thread 02's evidence. Installed state for every number below unless a section says otherwise: EFI change 14
(VermilionBoot b155), PhxAccel `26685255`, plugin cdhash `33b9a186`, RADV `8054fbe4` (the XT profile), daemon flags
as in PROJECT_KNOWLEDGE (wait step 200 us), desktop 2560x1440 240 Hz HDR, macOS 26.7.1. Every tool ran from a
terminal with `MESA_SHADER_CACHE_DIR` unset.

## 1. Tools added

- `tools/vkbench/vkbench.c` (`scripts/build/vkbench.sh`; Linux: one `cc` line in its header): `metalbench`'s
  Mandelbrot loop as a Vulkan compute shader (GLSL in `mandel.comp` / `stream.comp`, SPIR-V checked in as
  `vkbench_spv.h`, regenerated by `genspv.sh` with glslang 16.5). On macOS it opens RADV directly
  (`vk_icdGetInstanceProcAddr` of `/Library/GPUBundles/nvmtl/libvulkan_radeon.dylib`, as the plugin does), so it
  measures RADV + the kext without the Metal plugin and the translator. `VKBENCH_DRIVER=<dylib>` runs another RADV
  build without installing it.
- `metalbench` and `vkbench` gained `bandwidth [s] [MiB]` (copy one buffer into another, 16 bytes per thread, GB/s by
  GPU time) and `submit [s] [iterations] [w] [h]` (each command buffer waited, with a GPU job of a chosen length).
- `metalbench` loads another RADV build through the plugin's own `NVMTL_ICD_LIB` variable (an unhardened process
  accepts an ad-hoc dylib), so a RADV change can be measured before it is installed.

## 2. Metal (plugin + translator) against RADV directly, the same shader

05:43-05:46, nothing else using the GPU:

| Load | metalbench (Metal) | vkbench (RADV directly) |
|---|---|---|
| compute 2560x1440, 2000 iterations, GPU per frame | 4.24 ms | 3.95 ms |
| compute 2560x1440, 64 iterations, GPU per frame | 0.19 ms | 0.41 ms |
| submit (flat, each waited), wall median / p99 | 89 / 521 us | 34 / 129 us |
| submit, 512x512 x 200 iterations, wall median (GPU) | 322 us (103) | 265 us (51) |
| submit, 1024x1024 x 2000, wall median (GPU) | 1.50 ms (1.35) | 1.38 ms (1.08) |

- On the ALU-bound load the translated shader is ~7 % slower than glslang's SPIR-V of the same loop.
- At 64 iterations Vulkan is the slower one: its storage image goes `UNDEFINED -> GENERAL` every frame (RADV may
  re-initialise the image metadata each time) while Metal writes a render-target texture. Not investigated: it is a
  difference in the benchmark, not in the stack.
- **The plugin adds ~55 us to every waited submit** (89 vs 34 us flat). RADV + kext alone: 34 us median.
- The 512x512 job shows the poll: GPU 51 us, wall 265 us. After the 20 us spin the wait sleeps in 200 us steps.

## 3. Where buffers live: system memory, at PCIe speed

`metalbench bandwidth 8 256` (two private 256 MiB buffers) and `vkbench bandwidth 8 256` (device-local memory type 0,
heap 0 = the kext's 6144 MiB "hi VRAM"):

| | GB/s read + written |
|---|---|
| Metal | 44.7 (best 45.4) |
| RADV directly | 44.7 (best 45.3) |

Both are PCIe 4.0 x16 at ~22 GB/s each way: every BO is an `IOBufferMemoryDescriptor` in system memory
(`phx_client.cpp` `doBoCreate`), whatever domain RADV asks for. Navi 31's VRAM peaks at ~960 GB/s, so a memory-bound
load (large textures, post-processing, compute over big buffers) runs up to ~20x slower than it could. The Linux
number for the same command is the reference (handoff 1b). The 2026-11-22 puzzle (a 1440p target written at ~50 GB/s)
fits this: that render target compresses (DCC), so fewer bytes cross the bus *(unverified)*.

## 4. Fence waits by interrupt: a live test (sysctls, reverted)

The path from b60-b65 (upstream, never run on the XTX) turned on step by step, 05:46-05:50:

1. `debug.phxih_vram=1`, `debug.phxih=1`: the IH ring in VRAM at fw_buf + 12 MiB (140 MiB, inside the firmware
   staging area, free after boot). `IH_RB_CNTL` 0x40310121.
2. `debug.phxeopirq=1`: RELEASE_MEM asks for the EOP interrupt. IVs arrive: client 0x14 src 0xB5, ~150/s at the idle
   desktop.
3. `debug.phxirq=1`: the MSI (index 1) fires; 1.19 M IVs and 0.87 M MSIs over the test, **no storm, no overflow,
   no spurious storm** (12 k spurious = a drain that found the ring already empty).
4. `debug.phxwait_irq=1`: waits sleep until the interrupt (2 ms deadline).

First run, quiet desktop (05:49):

| | poll (200 us steps) | interrupt |
|---|---|---|
| vkbench submit, 512x512 x 200, median / p99 | 265 us / 924 us | 115 us / 2.37 ms |
| metalbench submit, same, median / p99 | 322 us / 977 us | 212 us / 4.49 ms |
| vkbench submit flat, median / p99 | 34 / 129 us | 34 / 575 us |
| `vkbench submit 5 200 512 512` throughput, CPU per frame | 3510 frames/s, 53 us sys | 7088 frames/s, 50 us sys |
| filter -> waiter latency (`debug.phxwait_lat` irq histogram) | timed: avg 123 us | avg 17 us, 25 us bucket for 93 % |

- The median of a short GPU job halves and waited throughput doubles at the same CPU cost per wait. The tails
  (p99) got **worse**, by 1.5-4 ms.
- WindowServer CPU at the idle desktop: `powermetrics` said 100 -> 200 ms/s, but `ps` CPU-time deltas over 30 s,
  alternated twice, showed no difference (231-273 ms/s in both modes). powermetrics' task numbers were noise here.
- A second set (05:58-05:59) is not comparable: the owner had started VacuumTube (YouTube) meanwhile, a second GPU
  client on the same gfx ring. With it, waits of every mode took milliseconds (the bench's job queued behind the
  other client's work), and with `debug.phxwait_irq_dl_us=200` most waits ended by deadline. The poll set taken just
  before it may already have overlapped the video.
- Everything was set back to 0 at 06:00 (`phxwait_irq`, `phxirq`, `phxeopirq`, `phxih`, `phxih_vram`); `IH_RB_CNTL`
  reads 0x40310120 again.

**Quiet A/B (06:25-06:30, owner away, nothing else on the GPU; `irqab.sh`: three rounds, poll and interrupt
alternated, 5 s per command), wall per frame:**

| Command | poll median / p99 (3 rounds) | interrupt median / p99 (3 rounds) |
|---|---|---|
| `vkbench submit 5` (flat) | 34 us / 35-260 us | 34 us / 47-139 us |
| `vkbench submit 5 200 512 512` | 265 us / 0.70-2.47 ms | **113-115 us / 0.44-0.56 ms** |
| `metalbench submit 5 200 512 512` | 324 us / 0.76-0.78 ms | **213-214 us / 0.64-0.65 ms** |
| `vkbench submit 5 2000 1024 1024` | 1.38-1.39 ms / 3.56-3.58 ms | 1.30 ms / 3.16-3.55 ms |

On a quiet desktop the interrupt wait is better in median **and** p99 in every row; the earlier worse tail came with
the second GPU client. 1.12 M MSIs in the run, no storm, no overflow. All five sysctls back to 0 at the end.

Superseded by the quiet A/B: the better median against the worse tail. To do before it can be a default: an interleaved A/B on an
idle desktop (only with the owner's OK: it loads the GPU), the tail's cause (a waiter woken by another queue's EOP
re-sleeps for the full deadline?), and a daemon flag to set it at boot.

## 5. The XTX's RADV profile (patch 0018), side-loaded

`patches/mesa/0018` makes revision 0xc8 take Mesa's own `navi31` entry. That entry differs from the fork's
`navi31_xt` only in the harvest fields (pci_rev, 96 CUs, full CU bitmap, 384-bit, `tcc_disabled_mask` 0): checked
with a field diff of the two entries at Mesa `f5cb8ee0`. A/B interleaved (XT, XTX, XT, XTX), 06:10-06:14, one other
GPU client open (VacuumTube, 19 % CPU, idle-ish), GPU time per frame, median of two rounds:

| Load | XT profile (installed) | XTX profile (0018) |
|---|---|---|
| metalbench render 2560x1440, 2000 iterations | 4.86 ms | **3.93-3.95 ms (-19 %)** |
| metalbench compute, 2000 | 4.14-4.20 ms | 4.17-4.20 ms |
| metalbench render, 64 | 0.260 ms | 0.261 ms |
| metalbench compute, 64 | 0.195-0.198 ms | 0.188-0.193 ms |
| vkbench compute, 2000 / 64 | 3.98 / 0.41 ms | 3.98 / 0.41 ms |
| metalbench bandwidth 256 | 44.4-44.5 GB/s | 44.5-44.6 GB/s |

- Only pixel shading got faster, by more than 96/84 would give. Likely RADV limits graphics waves to the CUs the
  profile lists, so the XT profile kept 12 of the 96 CUs out of pixel work, while compute dispatches use every CU
  *(unverified: the register RADV derives from the CU bitmap was not read)*.
- Metal and Vulkan now report "AMD Radeon RX 7900 XTX (RADV NAVI31)"; the plugin's core count follows RADV's CU
  count (96, not checked in an app yet).
- The owner noticed the machine getting slow during this run (with the video playing); load tests only with the
  owner's OK from now on.

## 8. Against Linux (the reference run of 06:41-07:04, [linux-reference](2026-11-23-linux-reference.md))

macOS readings taken at 07:14, 3 minutes after the first boot of change 15, 2560x1440 240 Hz HDR, the owner's idle
desktop (T3 Code open). BIOS: the owner's photos (05:34-05:38) show Global C-state Control, CPPC Dynamic Preferred
Cores, Power Supply Idle Control, Precision Boost Overdrive, ECO Mode all **Auto / Disable**, CPU fused boost clock
limit 5650 MHz: nothing in the BIOS caps the clock or the idle states.

| | Linux | macOS | Reading |
|---|---|---|---|
| GPU idle power | PPT 9.9 W at 60 SDR, 22-23 W at 240 SDR, 35 W at 240 HDR (11-51, screen activity) | socket 50-51 W, board 63-64 W at 240 HDR | macOS ~15 W over Linux at the same mode |
| UCLK | 96 MHz (level 0) at 60 SDR; 96 / 456 at 240; mostly 456 at 240 HDR | 456 MHz, pinned (daemon `uclk` flag, hard minimum) | the pin keeps UCLK off 96 |
| FCLK | 1000 MHz (level 1 of 8) | 2301 MHz (top) | never released on macOS |

| CPU 1 thread, frequency CCD | 5.16 GHz | 5.02-5.12 GHz | the same ceiling: not macOS's doing |
| CPU idle package | 37.8 W (C3 = CC6 98 % of the time) | 39.5-41.3 W (15 samples) | ~2-3 W: a `_CST` idle kext isn't worth its risk |
| `vkbench compute 2000` | 4.05 ms | 3.95 ms | same shader speed |
| `vkbench compute 64` | 0.134 ms | 0.41 ms | macOS writes the 14.7 MB image to system memory over PCIe: buffer placement |
| `vkbench bandwidth 256` | 823 GB/s | 44.7 GB/s | 18x: VRAM vs system memory |
| `vkbench submit` flat | 37 us | 34 us | same |

**What Linux sends the power firmware for the display** (the 2026-11-20 mode-set traces, 70 traces, every mode):
after every mode set, through the DAL mailbox, `SetHardMinByFreq` **UCLK 96**, **DCFCLK 199**, DISPCLK / DPPCLK
(per mode: 245 at 60, 505 at 120, 614 at 144, 537 at 240), `SetMinDeepSleepDcfclk` (18 MHz at 60, 36 at 120, 43 at
144, 72 at 240), `NumOfDisplays` 1, `BacoAudioD3PME` 0. During a switch to 240 Hz UCLK goes to 1249 and back to 96.
No `SetFclkSwitchAllow` in the mode-set traces (Linux sends it from `dcn32_update_clocks` when the FCLK p-state support
changes, so at its first update after boot, before these traces started *(unverified for this card)*).
macOS's replay plans send only DISPCLK / DPPCLK.

**The display side already matches Linux:** of 284 display registers in Linux's 240 Hz HDR capture, 248 read the same
on macOS, including DET (9 segments) and all four DCHUBBUB watermark sets A-D, and `DCHUBBUB_ARB_DRAM_STATE_CNTL`
0x1000 (stutter allowed). The 36 that differ are the planes' surface / DCC set-up, MPC / DPP colour, and
`ODM0_OPTC_INPUT_GLOBAL_CONTROL` 0x400: **the OTG0 underflow sticky is set** (an underflow happened at some time since
boot, likely during the login mode switch; not timed).

**Fans:** Linux loads no Super I/O driver on this board either. The chip is a Nuvoton NCT67xx behind ASUS's WMI
methods (the board is in `nct6775`'s ASUS-WMI list); model unverified. SMCSuperIO reads the chip through its I/O ports
directly, which is what ASUS's WMI path exists to avoid (the firmware's ACPI code uses the same ports): no EFI change
before the chip is named (`modprobe nct6775` on Linux, owner's OK) and that conflict is understood.

**RADV profile:** Linux's `gpuinfo` confirms the harvest fields of Mesa's `navi31` entry (96 CU, all 24 GL2 channels,
384-bit, full CU bitmap, 6 SE, 24 RB). Its firmware versions (ME 2540, PFP 2710, MEC 2790) are newer than the canned
entry's (1486 / 1525 / 494), which came from an older Linux; what macOS's pinned firmware reports was not compared.

## 9. Idle power: Linux's messages, live (07:25-07:48, owner's OK)

XTX machine, b155, 1440p240 HDR, the owner's desktop in light use (T3 Code). `idletest.sh` (scratchpad): OPTC0 / HUBP0
underflow stickies cleared, read every second; SMU metrics every 15 s. Every message is one Linux sends on this card
(the DAL list in section 8) or upstream's validated XT recipe (`b15_boot.sh` step 6).

| Phase | Sent | Clocks UCLK / FCLK / DCEFCLK (MHz) | Socket / board W (mean) | Underflows |
|---|---|---|---|---|
| base, 5 min | nothing (UCLK pinned 456 by the daemon) | 456 / 2301 / 661 | 53.5 / 67.1 | 0 |
| dpm, 10 min | `dalwm.sh`, `uclk.sh unpin`, `SetFclkSwitchAllow 1` | 96 / 1000-1200 / 661 | 30.2 / 39.9 (20-24 when idle) | 0 |
| dcf, 5 min | + `SetHardMinByFreq` DCFCLK 199, `SetMinDeepSleepDcfclk` 72, `NumOfDisplays` 1 | 96 / 1000 / 200 | 23.5 / 31.8 | 0 |
| re-pinned | `uclk.sh pin 456`, `SetFclkSwitchAllow 0` | 456 / 2301 / 200 | 52 / 66 at once | 0 |

The re-pin brought the power straight back: the clocks are the cause. **macOS at idle is now below Linux's 35 W at the
same mode** (Linux kept UCLK at 456 most of the time at 240 Hz HDR; why it did and macOS doesn't is not known).

**Under load (07:47-07:48, owner's OK), the same commands pinned then free, 5 s each:**

| | pinned | free |
|---|---|---|
| `vkbench bandwidth 5` | 44.1 GB/s | 43.7 GB/s |
| `vkbench compute 5`, GPU per frame median | 0.407 ms | 0.405 ms |
| `metalbench bandwidth 5` | 44.2 GB/s | 43.8 GB/s |
| board power at 100 % activity | 206-304 W | 172-270 W |
| underflows | 0 | 0 |

UCLK stayed at 96 MHz at 100 % activity: these loads read and write system memory (every buffer is system memory,
section 3), so the PMFW sees no VRAM demand. No loss today (-1 % bandwidth, within run noise). **For VRAM buffers (PR B)
UCLK must rise under load**; Linux reached 823 GB/s with the same hard minimum of 96, so the PMFW does raise it there.
M2 checks it on macOS *(unverified)*.

Made a boot step: `idle_dpm.sh` (flag `phxboot-idledpm`, `-dcf` for the DCFCLK messages), with the underflow watchdog
for the whole boot; mock-tested (`tests/mock/idledpm_test.sh`, the daemon's `idledpm_*` scenarios).
